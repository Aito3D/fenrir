# Aito — urgent flag

**Date:** 2026-08-04
**Branch:** `worktree-aito-urgent-flag`

## Problem

Some jobs have to jump the queue — a client is waiting on site, a delivery was
promised, a machine is idle behind this one. Today that fact lives in someone's
head or in a message, so the board looks identical whether a card is routine or
on fire. An operator scanning a column has no way to tell.

## Goal

An operator opens a project, holds an **Urgent** button for 0.5s, and the card
becomes a board-wide signal: a red breathing halo plus an `URGENT` chip, sorted
to the top of its column. Holding again clears it.

## Non-goals

Deliberately out of scope, and neither is needed for the signal to work:

- No urgent filter or urgent count in the column header.
- No notification (push/email/webhook) when a project is flagged.
- No urgency *levels*. It is a boolean; a three-tier priority scheme is a
  different feature with a different UI.
- Nothing is pushed to Zoho. Urgency is a workshop concept, not an accounting
  one — see the routing decision below.

## Data model

One column on `AitoProject` (`backend/app/models/aito_project.py`):

```python
# A local board signal: "this job is late / promised / on fire". Zoho knows
# nothing about it and must never be told, which is why it is written by its
# own route rather than by update_project — see routes/aito.py.
urgent: Mapped[bool] = mapped_column(Boolean, nullable=False, default=False, server_default="0")
```

Migration: an additive `ALTER TABLE aito_projects ADD COLUMN urgent BOOLEAN NOT
NULL DEFAULT 0` in `backend/app/core/database.py:run_migrations()`, following
the `quote_invoiced` precedent. No index: the column is read on every board
query but always alongside `board_column`, which is already indexed, and a
two-value column is not selective enough for its own index to earn its keep.

`urgent` is **not** cleared when a project moves column, is trashed, or is
restored. A flag someone set by hand is theirs to clear by hand; silently
dropping it on a column move would make the board lie in the one direction that
costs money. It stays set on a card in `done` — harmless, since done cards leave
the columns.

## API

### Why a dedicated route

`update_project` (`backend/app/api/routes/aito.py:1125`) ends every edit with an
unconditional `_mark_pending_if_ours(project)`, which queues a Zoho quote push
and — on the transition — records a `sync.queued` event. That is correct for
description and client fields, which Zoho mirrors. It is wrong for `urgent`:

- Zoho has no field for it, so the push would carry no new information.
- It would churn `quote_sync_state` on every flag, including on `locked`
  quotes where writes are already known to be unsafe.
- It would fill the project timeline with `sync.queued` noise generated by a
  purely local UI toggle.

So `urgent` is **not** added to `AitoProjectUpdate`. It gets its own route.

### The route

```
PATCH /api/v1/aito/{project_id}/urgent
body:     {"urgent": true}
response: AitoProjectResponse
```

- Guarded by the existing `Permission.AITO_UPDATE`. No new permission is
  introduced: a new one would need adding to the API-key classification lists
  as well as the role defaults, and "may edit an Aito card" is exactly the
  right authority for this.
- 404 on a project that is missing or `status != 'active'`, matching every
  other project route.
- Does **not** call `_mark_pending_if_ours`. This is the point of the route and
  is asserted by a test.
- Idempotent: setting `urgent: true` on an already-urgent project is a 200 with
  no event recorded (the value did not change), so double-taps do not spam the
  timeline.

`urgent` is added to `AitoProjectResponse` so the board and the detail panel
both read it from the row they already fetch — no extra request.

### History

Two new kinds in `backend/app/services/aito_events.py:KINDS`:

```python
"project.urgent.set":     "story",
"project.urgent.cleared": "story",
```

Story level, not detail: "who marked this urgent, and when" is precisely the
question asked afterwards, and a Detail-level event would be hidden at the
timeline's default depth. Not added to `COALESCING_KINDS` — each flip is a
discrete decision, and folding a set and a later clear into one window would
erase the fact that it was ever un-flagged.

## Ordering

**Exactly one query changes** — `list_projects` (`backend/app/api/routes/aito.py:526`):

```python
.order_by(AitoProject.board_column, AitoProject.urgent.desc(), AitoProject.position, AitoProject.id)
```

The two other `AitoProject` orderings in the file must be left **alone**, and a
change to either is a bug:

- `_active_in_column` (`:345`) is position-recalculation machinery for column
  moves, not a display query. Sorting it urgent-first would make the
  reassigned `position` values follow the urgent grouping, permanently
  rewriting the operator's manual order into the database — the exact
  destruction the display-only approach is chosen to avoid.
- `list_trash` (`:543`) is ordered by deletion recency. Urgency is meaningless
  for a deleted card.

**Known trade, accepted.** The board already stores a manual drag order in
`position`. With urgent-first sorting, manual order still holds *within* the
urgent group and *within* the normal group, but an urgent card cannot be
dragged below a normal one — it snaps back on the next fetch. The alternative
(rewriting `position` on flag) would destroy the operator's ordering
irreversibly, which is worse. No new `position` semantics are introduced.

The frontend must apply the same comparator locally so an optimistic flag
reorders immediately instead of waiting for a refetch.

## Frontend

### `UrgentButton.tsx` (new, `components/aito/`)

A thin wrapper over the existing `HoldButton`:

- `durationMs={500}` — already in `HoldDurationMs`, no new entry needed.
- `progress="bar"` — `HoldButton`'s own documentation reserves `bar` for wide
  labelled pills and `ring`/`perimeter` for icon-sized buttons. This is a
  labelled pill.
- `barClassName="bg-red-400/25"`, which is already the default.
- Symmetric: hold to set, hold to clear. Same gesture and same duration both
  ways, so an urgent job cannot be cleared by a stray click.
- Per the `HoldButton` contract, the caller supplies padding, border width and
  colour **in full** — the base deliberately supplies none, because
  same-specificity Tailwind utilities resolve by stylesheet order, not by call
  site.

Rendered in `ProjectDetailPanel` only. The card footer already carries
mark-sent, mark-done and delete; a fourth control there would crowd them, and
flagging is a deliberate act that belongs where you have the project open.

### `CardView.tsx`

Two additions, both on the **card element** (`data-aito-card`), never on the
outer shell — the shell holds collapsed height for the hover reveal and carries
no card styling, and `useCardMorph` resolves the view-transition name by
querying `[data-aito-card-id]`.

1. An `URGENT` chip in the name row, between the client name and the elapsed
   stamp. The chip is what keeps the signal from being colour-only, which
   matters for red-green colour blindness — the halo alone would be invisible
   to a chunk of operators.
2. `animate-urgent-halo` on the card element when `project.urgent`.

`overflow-hidden` on the card does not clip the halo: `overflow` does not clip
`box-shadow`, the same reason `card-shadow` already survives there.

### `index.css`

```css
/* Urgent: a ring that expands outward and fades, leaving the border crisp.
   Only the halo moves — the card's own edge never goes soft, so a column of
   urgent cards still reads as a column of cards. `--card-shadow` is repeated
   in every stop because box-shadow is a single property: a keyframe that
   omitted it would drop the card's elevation for the duration of the
   animation. */
@keyframes urgent-halo {
  0%   { box-shadow: 0 0 0 0 rgb(239 68 68 / .55), 0 0 10px -2px rgb(239 68 68 / .7), var(--card-shadow); }
  70%  { box-shadow: 0 0 0 7px rgb(239 68 68 / 0), 0 0 10px -2px rgb(239 68 68 / .7), var(--card-shadow); }
  100% { box-shadow: 0 0 0 0 rgb(239 68 68 / 0),  0 0 10px -2px rgb(239 68 68 / .7), var(--card-shadow); }
}
.animate-urgent-halo {
  border-color: var(--status-error);
  animation: urgent-halo 2.2s ease-out infinite;
}
/* The signal survives for anyone who has asked for less motion — as a static
   glow rather than a pulsing one, exactly like .animate-invoiced-glow. */
@media (prefers-reduced-motion: reduce) {
  .animate-urgent-halo {
    animation: none;
    box-shadow: 0 0 10px -1px rgb(239 68 68 / .6), var(--card-shadow);
  }
}
```

Red is `--status-error` (#ef4444), the app's fixed semantic red — it does not
shift with the accent theme, which is right: urgency is not a brand colour.

### i18n

`aito.urgent` (chip), `aito.markUrgent`, `aito.clearUrgent`, `aito.urgentHint`
("hold 0.5s"), plus timeline strings for the two new event kinds. Real
translations in all 13 locales — the i18n gate rejects English placeholders.

## Testing

**Backend**

- Sets and clears the flag; response reflects it.
- **`quote_sync_state` and `quote_sync_failures` are unchanged across the
  call** — the reason the dedicated route exists.
- Records `project.urgent.set` / `project.urgent.cleared` with `actor_class="user"`.
- No event recorded when the value did not change.
- 404 on a trashed or missing project.
- Board list returns urgent cards first within each column, with manual
  `position` order preserved inside each group.
- Existing `update_project` tests still pass — `urgent` is not in its payload.

**Frontend**

- Hold fires at 500ms and not at 400ms.
- A short tap surfaces the hint and does **not** toggle.
- Card renders the chip and `animate-urgent-halo` when `project.urgent`, and
  neither when it is false.
- Flagging reorders the column optimistically.

Note that `frontend/tsconfig.app.json` excludes `src/__tests__`, so adding
`urgent` to the `AitoProject` interface produces **no compiler error** in test
fixtures. Sweep them by grep for the field name.
